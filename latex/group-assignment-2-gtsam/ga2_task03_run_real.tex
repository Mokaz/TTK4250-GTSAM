\titledquestion{Run factor graph SLAM on the Victoria Park dataset}
\label{q:task03}
Victoria Park is a real dataset: a vehicle with a laser scanner, which sees the tree trunks, drives through a park, with a GPS for reference (see the \href{http://www-personal.acfr.usyd.edu.au/nebot/victoria_park.htm}{dataset's web page}\footnote{\href{http://www-personal.acfr.usyd.edu.au/nebot/victoria_park.htm}{http://www-personal.acfr.usyd.edu.au/nebot/victoria\_park.htm}}). The loader converts all times to seconds and turns the raw data into odometry and tree detections for you. The raw data consists of
\begin{itemize}
    \item LASER (mK, 361): laser scans, 361 returns spread over a half circle,
    \item speed (K,) and steering (K,): the speed from a wheel encoder at the rear left wheel, and the steering angle,
    \item Lo\_m and La\_m (Kgps,): the GPS position in metres,
    \item timeLsr, timeOdo and timeGps: the time stamps of the scans, the odometry and the GPS, in milliseconds.
\end{itemize}

The initial tuning is in \pythoninline{configs/real_default.yaml}, and it already works well: the map does not fill up with duplicate landmarks, and the trajectory stays close to the GPS. Consistency, however, can be improved. The landmark NIS sits well below its expected value. Improving this is the main point of this task.

As in Task~\ref{q:task02}, find 3 sets of tuning values that differ in different ways, and explain the results you get with them. Do not expect to get much closer to the GPS than the baseline: a better set is one that improves consistency without giving up what the baseline does well. At least one set should lower the odometry noise. Some sets will break the run: the map fills up with duplicate landmarks and the trajectory drifts away from the GPS. When that happens, describe what breaks and try to explain why it happens.

\paragraph{Plan your runs.} Use \pythoninline{run_real} the way you used \pythoninline{run_sim} in Task~\ref{q:task02}. A full run over all 7247 laser scans, the default, took about 2.5 minutes on our machine with the given tuning, and about twice that when the map grows; expect it to take longer on a laptop. To find good values without hours of waiting:
\begin{itemize}
    \item Explore with \pythoninline{run_real --steps 2000}, which takes about 20 seconds. The first 2000 scans cover most of the park, including the first \emph{loop closures}: places where the car returns to trees it has mapped before, so the graph connects its current pose to landmarks seen earlier. A tuning that breaks in this first period will not recover, but one that looks good can still fall apart later. Therefore, be sure to confirm a promising set with a full run.
    \item Change one group of parameters at a time (odometry noise, measurement noise, gates, landmark birth), so that you know what caused what.
    \item Watch the number of landmarks printed at the end of each run. The given tuning ends the first 2000 scans with about 140. If several hundred are observed, this likely means that data association is failing.
\end{itemize}
All figures and numbers in your report should come from full runs.

There is no ground truth, so the plots compare with the GPS instead. Keep in mind that the GPS is far from perfect, and that it drops out for about 40\% of the drive, so the GPS NIS and the distance to the GPS only cover the times it is available.

The GPS is not used by the SLAM system, as it only serves as a reference. The GPS NIS compares the estimate with each GPS sample, assuming the GPS has standard deviation \pythoninline{noise.sigma_gnss} (1\,m by default). This value is a guess about the GPS. Changing it does not change the estimate, only the GPS NIS. A larger value gives a lower GPS NIS for the same estimate. Do not tune it to improve the plot.
